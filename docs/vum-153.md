# Build 0.153 — VUM stable GPU virtual addressing / native local backend

Microsoft documents that heaps opened from existing CPU memory have cross-adapter properties, and cross-adapter sharing does not work with CreateReservedResource. Do not try to use VUM1 or the experimental VUM2 section heap as reserved-buffer tiles. See:
- https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_existing_heaps
- https://learn.microsoft.com/en-us/windows/win32/direct3d12/shared-heaps
- https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandqueue-updatetilemappings

The new VUM virtual_address backend creates a native reserved buffer with a stable GPU address, backed by independent device-local heaps of at most 32 MiB. It replaces the existing committed native buffer in the local card_room_for title-buffer admission path, not its CPU shadow or relay. The same size and residency budgets used by card_room_for are retained; an additional bounded 256 MiB live reservation cap limits the new backend. Tiled resource tier >= 2, size 16–256 MiB. The local heap byte count equals the old local allocation rounded to 64 KiB; the backend does not intentionally create a second local copy. Each 64 KiB tile is mapped once on a private copy queue before publication; its fence is waited for only at creation. Native descriptors and command lists reference the reservation directly. A COM lease on the native resource keeps all its mapped heaps and the budget charge alive until its last native reference goes away. Refusals before queue mapping fall back to the old committed buffer. Errors after mapping has been queued stop rather than freeing possibly in-use pages.

Default on for this bounded path; VICTORY_VUM_STABLE_VA=0 disables it, VICTORY_VUM_STABLE_MB changes the additional live cap (default 256 MiB, max 1024). No CMD changes needed. The existing VUM1 RAM path stays enabled. VICTORY_VUM_PHYSICAL=1 remains experimental and off. New log VUM stable VA shows the number of live reservations and allocated tiles. A unit test covers the logical regions.

This is the initial production-path reservation backend, not a complete physical mapping or migration manager. Each live reserved buffer still owns distinct local tiles. No dynamic remapping, physical aliases sharing VRAM tiles, demand reads, or elimination of legacy snapshots/readbacks is enabled by this change. The mapping primitive takes separate logical and physical ranges; later migration must preserve content and order remaps after all producer/consumer queues and relay operations, and keep old heaps until completion. The previous cross-adapter remapping problem is not solved simply by using this VRAM backend. No benchmark or Windows compilation has been performed; initial mapping may add loading latency. Correctness and support on the target GPU remain to be verified. No FPS gain claimed.
