# Build 0.149 — CPU access tracking prerequisite for demand readbacks

The 0.148 log repeatedly shows the same 21,045,760-byte local-card buffer in MEM_PRIVATE memory: two whole CPU refreshes (42.09 MB/frame), about 21.05 MB/frame uploaded and about 21 MB/frame fetched. XMemVirtualAlloc already uses write watch; ordinary guest VirtualAlloc/VirtualAlloc2 imports and the large XMemAllocDefault host heap fallback did not. This build extends the existing CPU write journal to these paths. Eligibility is ordinary host-chosen private reservations of at least 1 MiB, with normal read-write protection (or a plain no-access reservation later committed), without extended allocation flags. Existing allocation flags and API behavior are retained on failure. Large aligned XMemAllocDefault allocations use a private watched reservation with matching free logic. Native commitment assigns a fresh journal version including untouched zero-filled pages, so address reuse does not silently inherit an old CPU copy's version. Read access is not restricted.

This is only the CPU-write tracking portion of the approved demand-readback work. Actual delayed GPU fetch and PAGE_NOACCESS trapping are NOT enabled. Native private allocations have no writable alias; opening a protected page to merge results creates a race with other CPU readers, and kernel accesses need separate mediation. The current relay and CPU-visible fence ordering remain unchanged. No hardcoded title address, no changes to shaders or present. The log does not identify which allocator created the specific 21 MB buffer, so coverage or performance gains are not established. Allocations not covered by these paths retain the previous fallback. VICTORY_NATIVE_WRITE_WATCH=0 disables new tracking. Windows tests and gameplay were not run.
